# `purchases` — Crawler buys things for its owner, with safeguards on the steps

**Date:** 2026-09-25 · **Product:** Crawler AI · **Status:** design + implementation contracts (builds on `2026-09-24-browser-control-design.md` §6–§7 and `2026-09-24-computer-control-design.md` §4); §12 records the rules added after the 2026-09-25 review, §13 those added after the final security review the same day, §14 those added after the money-path review that followed it and §15 the change of guarantee that followed (the owner sees the page on a card before any act); the sections above them are updated to match the code.

## 1. Goal and the owner's rule

Crawler works like a human personal assistant. Told "get me a ticket for that concert, under $60, use my Visa", it finds the tickets, brings the browser to the checkout page, shows the owner what it is about to pay and where, and completes the purchase only after the owner says yes. The card stays "encrypted in its purse": the model never sees it, chat never carries it, no API returns it, and it is decrypted only in the moment the toolkit fills the merchant's card fields.

Buying is a **user-enabled ability with safeguards on each step**, never a blanket block. Off by default; the owner turns it on in Permissions and sets how much Crawler may spend. The safeguards are: the site must be HTTPS and the merchant the owner asked for (with a lookalike check), the amount is read from the page by the toolkit (not stated by the model), one approval card shows the merchant, the amount, the items, a screenshot and the notice "Crawler can make mistakes. Check the amount and the site before you approve.", and the purchase runs only while the page the card was made from is still the page on screen.

Out of scope for this slice: `browser.login` (the vault stores `login` records so it can follow spec §7 later), non-USD checkouts (refused with a plain reason), saved addresses (the model fills address fields through `browser.act` from what the owner tells it), more than one stored card.

## 3. Architecture

```
model ─▶ browser.read (READ) ─▶ browser.act (WRITE, card per call) ─▶ browser.checkout (FINANCIAL, one card)
                                        │                                      │
                          services/tools/browser/act.py            services/tools/browser/checkout/
                          (BrowserActToolkit)                       ├─ facts.py      page facts (origin, scheme, total, items, card fields)
                                        │                           ├─ merchant.py   IDN/punycode + lookalike check
                                        ▼                           ├─ amounts.py    "$1,234.50" → Decimal, currency
                          services/tools/browser/{session,guard,     ├─ ledger.py     per-day total from audit rows
                                          handoff,snapshot}.py       ├─ markers.py    the one classifier of card fields and buttons that pay
                                                                     └─ toolkit.py    BrowserCheckoutToolkit: begin / describe / run
                                                                                │ decrypt at fill time only
                                                                    services/vault/  (VaultService, key providers)
                                                                                │
                                                                    services/platform/{mac,windows}.py  get_secret/set_secret/delete_secret
```

Both toolkits share the `BrowserSessionManager` (one browser per user) with `BrowserReadToolkit`; they are constructed once in `main.wire_services` and handed to `ConnectorToolExecutor`.

## 4. Vault

- **Key custody** (`services/vault/keys.py`): `KeyProvider` protocol `get() -> bytes` (32 bytes; raises `VaultUnavailable(reason)`) and `check() -> None` (raises the same when the store cannot answer, and never mints: `VaultService.available()`, which Settings asks on every view, goes through it, so the Keychain holds nothing of Crawler's until the first card is stored). `PlatformKeyProvider(platform)` asks `platform.get_secret("vault-key")`; on the first `get` (the first `put_card`) it generates 32 random bytes and stores them with `set_secret`. `DevFileKeyProvider(path)` reads/creates a 0600 file (tests only). `DisabledKeyProvider(reason)` always raises. `select_key_provider(platform, env=os.environ)`: `mac`/`windows` → `PlatformKeyProvider`; `container`/`linux` → `DevFileKeyProvider` when `CRAWLER_VAULT_DEV_KEY_FILE` is set, else `DisabledKeyProvider("The card vault is not available in this environment (container).")`.
- **Platform secrets** (`services/platform/`): `Platform` gains `get_secret(name) -> Optional[bytes]`, `set_secret(name, value: bytes) -> None`, `delete_secret(name) -> None`, `vault_id() -> str` (a uuid kept in `<data_dir>/vault-id`, 0600, created on first use). Mac: `/usr/bin/security -i` with one command per call written to its stdin, every word double-quoted — `find-generic-password -s "Crawler AI vault" -a <vault_id>-<name> -w` (value stored base64), `add-generic-password -U … -w <base64>` to store or update, `delete-generic-password` — so the key is never an argument (argv is readable in the process table while the tool runs); the injected `Runner` takes the stdin text as a third parameter. A Keychain that will not answer (locked, denied, the tool missing) reads to the owner as "Crawler could not open this Mac's Keychain. Unlock the Mac and try again."; the exit code goes to the log only. Windows: `Crypt32` shim protocol (`protect(data: bytes) -> bytes`, `unprotect(blob: bytes) -> bytes`) over `CryptProtectData`/`CryptUnprotectData` with `CRYPTPROTECT_UI_FORBIDDEN`, user scope, ciphertext in `<data_dir>/<name>.dpapi` (dir ACL'd by the existing icacls step); tests inject a fake shim. Linux/container: raise `SecretStoreUnavailable`.
- **Crypto** (`services/vault/crypto.py`): `seal(key, plaintext: bytes, aad: bytes) -> bytes` = 12-byte nonce ‖ AES-256-GCM ciphertext; `open_(key, blob, aad) -> bytes`. `aad = f"vault_items:{kind}:{item_id}".encode()` so a blob cannot be moved between rows.
- **Store** (`models/vault_item.py`, migration `0010_vault_items`): table `vault_items(id Uuid pk, user_id Uuid fk users cascade, kind String(16) not null, label String(120) not null, origins JSON not null default [], masked String(64) not null, blob LargeBinary not null, created_at, updated_at, last_used_at nullable)`, index `(user_id, kind)`. Card plaintext JSON: `{"number", "exp_month", "exp_year", "cvc", "name"}`; login: `{"username", "password"}`. The migration also adds `installation.capability_settings JSON NOT NULL server_default '{}'` (guarded like 0008/0009; `test_migrations.py` must stay green: the model gets the same column).
- **Service** (`services/vault/service.py`): `VaultService(session_factory, key_provider)`; `available() -> tuple[bool, str]`; `put_card(user_id, *, label, number, exp_month, exp_year, cvc, name, origins=()) -> VaultItemView` (Luhn + brand detection, one card per user: replaces the existing `card` row); `list_items(user_id, kind=None) -> list[VaultItemView]`; `delete_item(user_id, item_id)`; `open_card(user_id, item_id, *, purpose: str) -> CardSecret` (decrypts; only the checkout toolkit calls it; logs `vault_item_opened` with kind/label/purpose only). `VaultItemView(id, kind, label, origins, masked, brand, last4, created_at, last_used_at)` is the only shape the API returns. `CardSecret` is a dataclass with `__repr__` returning `<CardSecret ····4242>` and a `wipe()` no-op hook, held only inside `run_checkout`.
- **API** (`api/routes/vault.py`, prefix `/vault`, owner-only via `require_admin`): `GET /vault/items` → `{"items": [VaultItemView…], "available": bool, "reason": str}` (a 200 always; `available: false` with the reason in a container, which the Settings page shows instead of the form); `PUT /vault/card` body `{label?, number, exp_month, exp_year, cvc, name}` → the view (422 on Luhn failure/expiry in the past; 409 `vault_unavailable` with the provider's reason in a container); `DELETE /vault/items/{id}` → 204. Every write is audited (`connector_name="vault"`, actions `vault_card_stored` / `vault_item_deleted`, `request_data={"kind","label","masked"}`). The route's request models have `repr=False` fields for `number`/`cvc`; the validation error handler already refuses to echo input, and the route never logs the body. `POST` from a non-loopback host is refused with 403 `localhost_only` (the browser form is only ever served on the owner's machine).

## 5. `browser.act`

`services/tools/browser/act.py`, `BrowserActToolkit(sessions, *, guard, handoff, clock)`, `execute(action, params, *, user_id, task_id, approved: bool, card: Optional[dict])`.

- Actions and the flat schema (`ACT_ACTIONS`): `fill(ref, text)`, `fill_form(fields: [{ref, text}], ≤12)`, `select(ref, value)`, `check(ref)`, `click(ref)`, `press(key ∈ Enter|Tab|Escape|ArrowDown|ArrowUp)`, `submit(ref)`. Text ≤ 2000 chars per field. Every act returns the fresh outline exactly as `browser.read` does (`_observe`), plus `"did": 'Typed 12 characters into "Email"'`.
- **Precheck** (`precheck(params, user_id) -> Optional[dict]`, no browser call): argument shape; the stop flag; a ref the latest outline does not have (`stale_ref`); a ref the latest page facts mark as `password`/`one-time-code`/`cc-*`, or whose name matches the checkout's own card-field classifier (rule `secure_field`: "That is a password or card field, and Crawler never types into one from chat. Card details are filled from the vault during checkout."); an `http://` page (rule `insecure_page`); a `click`, `submit` or `press(Enter)` whose target's outline name is a purchase, a `submit` through a field whose form button's name is one (the page memory keeps each field's form button, `form_buttons`), and a `check` or `select` whose outline name, or the value it chooses, is one (rule `use_checkout`, whatever the purchases switch says, with the one sentence "Crawler only pays through its own checkout step, which needs 'Buy things for me' on in Permissions.": buying goes through `browser.checkout`, its card, its caps and its ledger, never through an act; the live page is judged again at run, below). The purchase words (`checkout.markers.PURCHASE_WORDS`) are Place order, Pay now, Buy, Subscribe… and the main words of German, French, Spanish, Portuguese, Italian and Dutch shops (Jetzt kaufen, Passer la commande, Finalizar compra…) and of Japanese, Chinese, Korean and Hindi ones (購入, 支付, 구매, खरीदें…; these match inside a longer phrase, as those scripts are written without spaces); a bare "Checkout" or "Proceed to checkout" is not one, it only leads to the checkout page. The toolkit keeps a per-user `_LastPage(url, origin, outline_digest, secret_refs, names)` written by every `browser.read`/`browser.act` observation (the read toolkit calls `act.remember(user_id, page)` through a small `PageMemory` object both share, owned by `act.py`).
- **Bind** (`bind(params, user_id) -> dict`): adds `_page = {"origin": …, "address": <sha1 of the URL without its fragment>, "outline": <digest>, "scheme": …}` (reserved key; a call carrying its own `_page` is refused like desktop.act's `_screen`). The executor's card-time bind is `bind_async(params, user_id, task_id)`: `bind`, plus `_page.picture` (the id of a masked screenshot of the page with the target outlined in a 3px red box, kept in memory for the approval's TTL (`APPROVAL_TTL_MINUTES`, at most 32 pictures) and served by `approval_image(arguments, user_id)`; "" when the capture failed) and, when the page's joined frame facts show an order total, a payment method on file or a wallet button, or the target matches a purchase pattern, `_page.money` (the amount read from the total line, and which of those it shows) for the card's warning.
- **Describe** (`describe(params, user_id) -> str`): `Type 12 characters into "Email" on shop.example.com`, `Fill 5 fields on shop.example.com: Email, Name, Address…`, `Click "Continue to payment" on shop.example.com`, `Press Enter on shop.example.com`; with `_page.money`, then "This page shows $499.00 and a saved payment method. This step may place an order. Crawler normally pays only through its checkout step." (the amount left out when unknown), and with an empty `_page.picture`, "No picture of the page could be taken."; with a `_page.picture` no longer kept (expired, evicted, a restart), "The picture of the page is no longer kept, so this step will not run."
- **Run** (approved only): rules again; `picture_gone` when the card was bound with a picture that is no longer kept; `page_changed` when `page.url`'s origin ≠ `_page.origin`; `outline_changed` when the page's address ≠ `_page.address` or its current outline digest ≠ `_page.outline`, for every act (Enter activates whatever has the focus on the page open now); the live element facts re-checked (`markers.FIELD_KIND_JS`: refuse secure fields); then the purchase rules on the live page, `use_checkout` again, with what every frame of the page shows joined in (`markers.PAGE_FACTS_JS` asked of each frame, open shadow roots included, and `markers.join_page`; a frame that cannot be asked counts as showing everything, one that went away as nothing), so a review page's total and saved card count for a button inside its frame, and a frame's for the page around it:
  - A click, submit or Enter (`markers.PURCHASE_TARGET_JS` / `SUBMIT_TARGET_JS` / `ENTER_TARGET_JS`, judged by `markers.pays`) is judged by the control that would send the form, never only the element named: a click is judged at the point Playwright clicks (the centre of the element's first box, followed into open shadow roots), through the link or button around what is there and a `<label>` as the control it is for; a submit through a field sends the form by its default button (the form's first submit control in tree order, `form=` buttons included) and is sent through that same button; Enter activates the focused element whatever it is (a `<div tabindex>` is judged by its own words), and in a field sends the form by its default button, followed through open shadow roots and into a focused frame, which is asked again (up to four frames deep; a focused frame that cannot be entered refuses, and so does a focus hidden in a shadow tree nobody can read). It is refused when its words are a purchase; when its form holds a typed card number or security code; when it, its form or its link is aimed at an order path (`ORDER_ACTION_RE`: /place-order, /orders, /pay, /purchase, /checkout/complete…, whatever the method); when the page holds a payment method on file next to any price and the act is anything but a plain link (an http(s) link to another page with no click handler and no role of its own); or when it is a button (any element with a click handler, a tabindex or a pointer cursor counts as one), or sends a form, on a page that shows an order total on screen next to a payment method on file (`TOTAL_LABEL_RE` with a price).
  - A check or a select (`markers.CHANGE_TARGET_JS`, judged by `markers.change_pays`) is judged by what it chooses: the control's label, aria name and value, and the chosen option, never the options it does not choose. It is refused when that is a purchase, or when the page holds a payment method on file next to any price.
  - A payment method on file is `SAVED_PAYMENT_RE` ("card on file", "your default card", "ending in 4242" and its forms in the main languages, a masked number such as `•••• 4242`, `····4242`, `****4242` or `...4242`, "Payment method: Visa", "Zahlungsart: Visa") or a wallet button, element or frame (`WALLET_RE`: Apple Pay, Google Pay, PayPal, Shop Pay, Amazon Pay); brand names alone do not count. Totals are read in the main languages too (Gesamtsumme, zu zahlen, 合計, 총액, Итого, الإجمالي, סה"כ…), and a total label whose amount is a picture counts as a total. A price is any currency sign Unicode knows, an ISO 4217 code (less the ones that are English words) or a word shops write one with (円, kr, zł, ر.س…); a button that is little more than a price ("$0.99", "Rent HD $3.99") is a purchase. A shadow tree nobody can read (a closed root) makes every fact of its page count as shown. The masked number, the wallet, the price and the order path are signals that do not depend on the page's language.
  - The write window: the egress state's `write_allowed` is raised only around a click, submit or Enter that passed these rules, a plain link excepted (so the POST navigation it starts passes the route guard), and lowered in `finally`. Every other act (fill, fill_form, check, select, Tab, Escape, the arrows, a plain link) runs with the window shut and `EgressState.changing` set: the guard then stops a form POST from the top page or any frame, and any navigation of any frame to an order address (GET included; a top-level redirect's target too). When it stopped one of these (`guard.SENDING_REASONS`) the act is refused as `auto_submit` with "That change tried to send the page. Crawler didn't let it." A fill, fill_form or Tab on a page with a card on file is not refused on its own (address fields are filled on checkout pages through `browser.act`); the shut window is what stops a field whose own script sends the order.

  `typed_secrets` is untouched by acts (model text is not secret). The handoff window (`EgressState.human_driving`, from the browser-control fix that lets the person sign in inside Crawler's window) is shared by the three toolkits through `_shared.hand_over` / `_shared.take_back`: a challenge met by a read, an act or a checkout, or the model's own `browser.read handoff`, hands the page to the person, and the agent's next action on the session, whichever toolkit makes it, shuts the window before touching the page; a checkout's bound write window still admits only its one POST while the person is driving. The window lets the person's own submit through (a sign-in, a one-time code), never an order: no frame opens an order step and nothing is sent to an order address while it is open, since the model may ask for a handoff on any page and the page's own script may send its order form meanwhile. Only the checkout's handoff after the approved order (`EgressState.checkout_handoff`, `hand_over(..., checkout=True)`: a 3-D Secure page returning to the shop's payment address) opens the order addresses to the person.
- Summaries: `[step 7] act fill "Email" → shop.example.com/checkout · 41 refs`.

## 6. `browser.checkout`

`services/tools/browser/checkout/toolkit.py`, `BrowserCheckoutToolkit(sessions, *, guard, handoff, vault, ledger, settings, clock)`.

**Money paths: the guarantee.** Four review rounds showed that word lists and page patterns can never be proven to catch every way a click on an arbitrary shop page places an order. So the guarantee is one the code can be checked against instead: **no money moves without the owner seeing the page on an approval card first, and card data is only ever entered by `browser.checkout`.** It rests on three facts:

1. **Every step that can change a page is `browser.act`, and every act waits for a card that shows the page.** `browser.act` (WRITE) needs its own switch, "Fill in forms and click on sites" (`browser_act`, off by default, separate from reading), and runs only re-dispatched with `approved=True` after the owner said yes to its card (`_BUILTIN_STANCE["browser"] = "user_confirm"`: no account default makes it unattended), and only while the page the card was made from is still on screen (`page_changed`; `outline_changed` when its address or outline differs, for every act, a key press included). Every act card carries a picture of that page taken when the card was made (`BrowserActToolkit.bind_async`: the target outlined in a 3px red box by an overlay added and removed around the capture, secret fields masked by the shared mask, kept in memory and served through `approval_image` to the web card and as the Telegram photo, never stored with the card). When no picture can be taken the card is still made and says "No picture of the page could be taken."; a card whose picture is no longer kept says so and its act is refused (`picture_gone`).
2. **`browser.read` has no card, so nothing it does sends an order.** Its click only follows a plain `<a href>` GET link whose address is no order path (`markers.READ_LINK_RE`: `ORDER_ACTION_RE` less an order history, /orders or /orders/8841), or clicks a control that is outside any form, has no purchase words and is on a page (every frame of it) with no order total, no payment method on file and no wallet button (`markers.read_click_allowed`); everything else is refused with "Reading can't click that. Ask to fill in forms and click (needs 'Fill in forms and click on sites' in Permissions)." Outside a write window (the person's handoff included, the checkout's own after the order aside) the egress guard aborts every non-GET navigation of any frame (the person's own submit during a handoff aside, unless it goes to an order address), any navigation to an order step (`ORDER_STEP_RE`: open, a link, back or a redirect alike), a page's own request of any method to an order step (an image, a GET `fetch()`, a beacon: opening one can be the order) and a page script's non-GET request to any order address (`ORDER_ACTION_RE`: POST /orders, /pay, /buy…), so a page that orders on load or when scrolled to sends nothing. While the click runs and until the network is quiet after it (`EgressState.read_click`, held by `guard.wait_for_quiet` until no request has been in flight for 250 ms, at most 2 s after the click) the guard also aborts every page script's request but a GET, any request or navigation to an address `READ_LINK_RE` matches, and every message a page sends on its own WebSocket, and the click is answered with the same sentence.
3. **Card data comes only from the vault, through `browser.checkout`.** `browser.act` never types into a password, one-time-code or card field (`secure_field`, before the card and again on the live element); `browser.checkout` fills the card only after its own card (amount, merchant, screenshot) was approved, within the caps, with the approval written to the ledger before the vault opens, submitting only to the origin it bound at `begin`.

**Every window is its page's.** The write window of an approved act or checkout (`write_allowed`, and `write_origin` with it) is opened for the page the card showed (`EgressState.write_page`), and the checkout's handoff after the order (`checkout_handoff`) for the page the bank's check is on (`EgressState.handoff_page`): the guard judges a request as inside a window only when its frame belongs to that page, so another tab of the same session, a worker, and a request whose frame or page cannot be told (a popup's first navigation) are outside it, and approving a step on one tab lets no other tab send an order. Inside the window the approved tab is navigated only by its own document (`guard._started_by`: the request's Origin, or, when that is missing or "null", its Referer's origin, is the origin of the page open in it; one that names neither passes only while the tab is the session's only one; `OTHER_PAGE_NAVIGATION` otherwise), so a tab of another site that holds the approved one (it opened the shop with `window.open`, or the shop opened it) cannot point it at /place-order while the owner's approved step runs, directly or through a page of its own that would open the step as the tab's own. A cross-origin frame of the approved page that navigates the top page is stopped the same way. Service workers stay blocked in every context. What only narrows (`write_origin`, `changing`, `read_click`) holds for every tab, and so does the person's handoff (`human_driving`), which lifts no order block and may need a sign-in popup. A WebSocket is not a request the route sees, so the guard connects every socket itself (`context.route_web_socket`, `Guard._socket`): what the server sends passes; what the page sends is dropped while a read-tier click runs, and always on a page's socket whose address is an order address, since a socket's page cannot be told and so is never inside a write window. `route_web_socket` sees a page's sockets only: a socket a worker opens is not routed (residual 1).

**Defence in depth.** Every rule of §5 and §12–§14 still runs on top of the guarantee: `browser.act` refuses a click, submit or Enter its patterns read as placing an order and a choice of a payment method (`use_checkout`), and a change whose page sends itself (`auto_submit`); `browser.read`'s click is refused first on whatever `markers.read_click_pays` flags. Every act card also adds, built from the page's own facts, "This page shows $499.00 and a saved payment method. This step may place an order. Crawler normally pays only through its checkout step." when any frame shows an order total, a payment method on file or a wallet button, or when the target matches a purchase pattern that did not refuse it (a button on a review page whose payment line is in a language the lists do not know); the amount is left out when the total cannot be read.

**Residuals, stated plainly.**

1. While an approved act runs, what the card's page's own script sends (XHR, fetch, a beacon) is not judged: the owner approved that step on a picture of that page (every other tab is outside the window). During the bound checkout window hosted payment scripts send the card that way, and a GET navigation of any frame to another origin is admitted, checked only by the address rules (`check_url`).
Outside an approved act, a page's own requests when it is opened, or on a timer, to an address that is no order address (/graphql, /api/cart/checkout) pass, as they would in the owner's own browser: a page that orders by itself at such an address is not stopped (accepted). Messages on a WebSocket whose address is no order address pass too when no read-tier click is running (a site's live updates). A page's own sub-resource or frame request that redirects to an order step is not followed hop by hop. Cross-site, such a request carries no SameSite=Lax cookies, so it cannot act on a signed-in session; same-site, it is the shop's own page acting on itself, as in the owner's browser. Fetching every request through the guard would close it, at the cost of the browser cache, streamed responses and hand-copied cookie rules on every page, which ordinary browsing needs. An EventSource stream is such a request too: its redirect is not seen either. A socket a dedicated or shared worker opens is not routed at all, so what a worker sends on one is not judged, an order address's socket and a read-tier click's window included (accepted: a page's script can reach the same site by an ordinary request to an address that is no order address, which also passes). In a window, a navigation the approved page starts itself on a page whose referrer policy sends no origin at all (`no-referrer`) is refused while another tab of the session is open.
2. The patterns may miss unusual pages (a language or phrasing not listed, a review page drawn in a shape the markers cannot read), which is why every act card shows the page. The money warning depends on what the patterns read, so a card without one is not a promise that nothing is paid; the picture is.
3. A read-tier plain link is followed without a card: a shop that places an order on a GET to an address that is no order path (`READ_LINK_RE`) is not caught by that rule. A script that a read-tier click starts and that sends only after the click's window has closed (the network quiet for 250 ms, or 2 s after the click) is judged by the order rules alone: a delayed POST to an address that is no order address passes (accepted).
4. The picture is the viewport as it is when the card is made. A target off screen is named by the card's sentence but its red box is not in the picture, and a page that changes after the card is refused at Approve only when its origin, address or outline changed.

**Facts** (`facts.py`, `collect_checkout_facts(page) -> CheckoutFacts`): `url`, `origin`, `scheme`, `title`, `total: Optional[Money]`, `totals: tuple[Money, ...]` (every distinct amount a total line named), `totals_seen: list[str]` (raw candidate strings), `items: list[str]` (≤10 lines from `[class*=item], li, tr` rows that contain a price), `card_fields: CardFields(number_ref, exp_ref | exp_month_ref+exp_year_ref, cvc_ref, name_ref, frame_origin, form)`, `submit_ref`, `submit_target: SubmitTarget(action, method)` (the button's `formaction` or its form's `action`, and the method), `outline_digest`. A total candidate is a short text block whose label matches `_TOTAL_LABEL = /(order )?total|amount due|you pay|grand total/i` (never "subtotal", never "total before …") and that is on screen: inside the viewport and painted there (the middle of its visible part hits the element itself, so text parked off-screen, clipped or covered never counts); the one nearest the card form (or the order button) is the total, and the distinct amounts are kept for the `ambiguous_total` rule. Card fields by `markers.field_kind`: the `autocomplete` token (`cc-number`, `cc-exp`, `cc-exp-month`, `cc-exp-year`, `cc-csc`, `cc-name`) first, then the hints a site names a field by (name, id, placeholder, aria-label, aria-labelledby text, label text: "ccnum", "pan", "csc", "Card no.", "Expiry"…), the same patterns the outline, the screenshot mask and `browser.act` use; the order button only from the card fields' own `<form>` (never one attached through `form=`), named like one first, else that form's last submit control; card fields inside a frame count only when the frame origin is the page origin or in `PAYMENT_FRAME_HOSTS = ("js.stripe.com", "checkout.stripe.com", "pay.google.com", "www.paypal.com", "assets.braintreegateway.com", "checkoutshopper-live.adyen.com")`.

**Amounts** (`amounts.py`): `parse_money(text) -> Optional[Money(amount: Decimal, currency: str)]` for `$`, `US$`, `USD`; other symbols parse with their ISO code; `Money` is frozen; `usd(money) -> Optional[Decimal]` is `amount` only when `currency == "USD"`.

**Merchant** (`merchant.py`): `merchant_refusal(origin_host, expected: str) -> Optional[str]`: normalises both through IDNA (punycode → unicode), refuses mixed-script or confusable hosts (`unicodedata` NFKC + a small confusable map for Cyrillic/Greek lookalikes), refuses when `expected` (a host or a bare brand like "ticketmaster") is neither the host nor a registrable-domain match (`tldextract`-free: last two labels, plus `co.uk`-style suffixes from a short list), and refuses when the host is a lookalike of a `WELL_KNOWN_MERCHANTS` entry without being that entry: the brand as any label of the host or any hyphenated part of one, on a registrable domain that is not the brand's own (`ticketmaster-tickets.co`, `amazon.com.evil.com`, `www.paypal.com.secure-login.xyz`, `ticketmaster.evil.com`; outside the brand label only an exact match counts, so a short brand is never read into a longer word: `aaa.com`, `bath.com` pass), a known brand on another registrable domain or top-level domain (`amazon.shop`, `amazon.de`, `apple.support`: a country site of a listed brand is refused too, with the plain sentence telling the owner to open the site themselves), and a brand label within an edit distance scaled to its length (exact for 3 characters or fewer, 1 for 4–6, 2 for longer: `amazom.com` is refused, `hp.com`, `dell.com`, `ups.com` are not). A bare IP host and a host with userinfo are refused (loopback only under `CRAWLER_ALLOW_LOOPBACK_FOR_TESTS`, the guard's own test toggle, which the 127.0.0.1 fake shop needs).

**Ledger** (`ledger.py`): `PurchaseLedger(session_factory)`, `spent_last_24h(user_id) -> Decimal` summing `request_data["amount_usd"]` over `audit_logs` rows with `connector_name="purchases"` in the last 24 h for every checkout whose card was submitted — `purchase_completed`, `purchase_pending_human`, and `purchase_refused` whose reason is a post-fill one (`no_confirmation`, `submit_failed`, `submit_blocked`) — and never for an explicit `declined` (Python-side sum; a handful of rows). An approved checkout counts too until its outcome is on the record: the `purchase_approved` row is written before the vault opens, and it is settled by the outcome row (`purchase_completed`, `purchase_refused`, `purchase_pending_human`) carrying the same `checkout_id`, read in write order (`seq`); from then on only the outcome can count, so a checkout counts once, and a process that died or an outcome write that failed after the fill still leaves the purchase on the cap. Rows written without a checkout id are paired by task, in write order; an unsettled approval older than 24 h leaves the sum like any row. The cap fails closed: money that may have moved counts. `record(user_id, event, *, merchant, amount_usd, currency, items, task_id, action_id=None, reason=None, checkout_id=None)` appends one row (`connector_name="purchases"`, `action=event`, status approved for `purchase_completed`/`purchase_approved`, pending for `purchase_requested`, blocked for `purchase_refused`). Never card data: the row has no brand, no last4, no label.

**Model-facing action**: one ToolSpec `checkout` with schema `{merchant: string (required, the site the person asked for, e.g. "ticketmaster.com"), amount: number (what you expect to pay, USD), note: string?}`.

**Flow**:

1. `precheck(params, user_id)` (no browser): schema; `purchases` settings readable; vault available; a stored card exists (else rule `no_card`: "No payment card is stored. Add one in Settings → Payment card."); stop flag.
2. `begin(params, user_id, task_id) -> dict` (called by the executor's `approval_arguments` hook — the one place a bind may touch the browser, because the card must show live facts): takes the session lock; challenge check; `collect_checkout_facts`; refusals in order — `insecure_page` (scheme ≠ https), `merchant_mismatch` (from `merchant_refusal`; an IP-literal host and a well-known brand on another top-level domain are refused too), `no_total` (no USD total found), `ambiguous_total` (the totals on screen name more than one distinct amount; text hidden off-screen, clipped or covered never counts), `currency` (non-USD), `no_card_fields`, `submit_target` (the submit control's effective target — the button's `formaction` or the form's `action` — is not https and same-origin with the page, or in `PAYMENT_FRAME_HOSTS` for a frame form; the submit button is chosen only from inside the card fields' own form, never through a `form=` attribute; the target is bound into `_checkout` and re-checked at `run`, and during the write window the guard admits, as a navigation of any frame, only a POST to that origin, fetches the order POST itself and stops an answer that would re-send it elsewhere — a 307/308 to another origin; what the page's own script sends by XHR or beacon is not a navigation and is not judged), `over_cap` (max(page total, model amount) > per-purchase cap), `over_daily_cap` (that + `spent_last_24h` > per-day cap). A refusal returns `{"ok": False, "refused": True, "rule": …, "error": …}` and the runtime files it under `purchase_rule` (no card). Otherwise it takes a masked screenshot (`_jpeg`, mask includes card fields), stores `_Pending(checkout_id, user_id, facts, user_image, created)` in memory (≤1 per user, replaced; dropped after the approval TTL) and returns the card arguments: the model's `merchant`/`amount`/`note` plus `_checkout = {"checkout_id", "origin", "host", "amount_usd": "23.40", "currency": "USD", "items": [...≤10], "card_label": "Visa ····4242", "outline": <digest>, "submit_to": <the bound target's URL, or "">, "notice": NOTICE}`. Audit `purchase_requested` with the checkout id.
3. `describe(arguments, user_id) -> str`: `Pay $23.40 to shop.example.com (2 items) with Visa ····4242`.
4. `approval_image(arguments, user_id) -> Optional[str]`: the pending screenshot for `_checkout.checkout_id`, else None.
5. `run(arguments, user_id, task_id)` (approved only): the pending entry must exist and match (`unbound_approval` otherwise); the current page's origin and outline digest must equal `_checkout` (`screen_changed`: "The page changed since you approved this. Look again and ask me to check out once more."); facts re-collected and compared whole (a changed URL, total, set of totals or submit target → `screen_changed`); caps re-checked; the pending entry dropped; audit `purchase_approved` with the checkout id (a write that fails refuses `check_failed`, "Could not write this purchase to Crawler's record before paying, so nothing was paid. Ask me to check out again.", with the vault never opened; approving the same card again is `unbound_approval`); `vault.open_card(...)`; fill the card fields by ref with `locator.fill` (frame-aware), then read the number, security-code and expiry fields back (never the name field, never a `<select>`, nothing shorter than four characters) and add each value — the number as the site groups it and as digits, the expiry, the CVC — to `session.typed_secrets` for the rest of the task; `write_allowed` around the submit click, bound to the target's origin (the guard's `write_origin`), and what the guard stopped meanwhile decides the outcome (`submit_blocked` when the order POST itself was stopped, or when the site's answer led somewhere the guard refused after the card had reached it; `no_confirmation` when nothing was stopped and the page after the order never loaded); wait for load; challenge check (a 3-D Secure/OTP page returns `needs_human` with the screenshot masked by the re-collected card refs and the purchase is recorded `purchase_pending_human`, not completed; the page is the person's from then on, so the code they type and submit in Crawler's window, and the bank's return to the shop's payment address, pass the guard until the agent's next action: `hand_over(..., checkout=True)`); screenshot, masked the same way; `confirmation_text_summary` = the first 600 characters of visible text that match `_CONFIRMATION_RE = /order (number|#|confirmed)|thank you|confirmation/i` around the match; audit `purchase_completed` with the amount (every outcome row carries the checkout id; an outcome write that fails is logged at error level by its type only, and the approval row already written keeps the purchase on the daily cap); result `{"ok": True, "merchant": host, "amount": "23.40", "currency": "USD", "confirmation_text_summary": …, "user_image": …, "summary": "[step N] checkout → shop.example.com/order-confirmed", "mode": …}`. Any failure after the card was filled returns `{"ok": False, "error": …, "filled": True}` and audits `purchase_refused` with the reason, so the owner is told to check the site; on every such path where the page still shows the form (validation stopped the submit, a decline, a cancel between fill and submit, a failed click) the card fields are cleared before the toolkit returns: each remembered ref (`fill('')` or a deselect, frame-aware, refs that no longer resolve skipped), then a sweep of every frame with the shared classifier (`markers.CLEAR_CARD_FIELDS_JS`) that also counts what is left; a field that would not clear adds one plain sentence to the result ("Crawler could not clear the card details from the page; the person should close that tab.") and a count-only warning to the log. An exception raised while card values are in play is logged by its type only (Playwright's call log echoes the typed value).

`NOTICE = "Crawler can make mistakes. Check the amount and the site before you approve."` lives in `services/tools/browser/checkout/__init__.py` and is imported by Telegram; the frontend copies the string (a vitest asserts it matches the backend fixture `tests/fixtures/purchase_notice.txt`, published to the frontend as `src/pages/purchaseNotice.ts`).

**Reminder offer**: `PURCHASES_SYSTEM_PROMPT` (a `<purchases>` block the runtime appends to the system message only when `browser.checkout` is among the tools offered, i.e. purchases and browser_control are both on) says that checkout is the one sanctioned purchase path and the only exception to the hard limit, that the card is filled from the vault and never typed, and: "After a completed checkout, tell the person what was bought and the amount, then offer a reminder (reminders.create) for the event or delivery date if one is on the confirmation page." `SECURITY_SYSTEM_PROMPT` itself is unchanged from before the feature (its hard limit still forbids purchases outright), and so is every pre-existing tool description; with buying off, a request differs from before the feature only by the `<permissions>` lines for the new switches ("Buy things for me: off — …", which §5.2 step 4 relies on, and "Fill in forms and click on sites") and, with both browser switches on, by the `browser.act` tool on the catalog; the `browser.act` tool description does not mention checkout.

| Frames and shadow roots | Enter follows the focus through open shadow roots and into a focused frame (four deep; one that cannot be entered refuses). Every frame's facts (total, payment method on file, wallet, price) are joined into the judgement; a frame that cannot be asked counts as showing all of them. |
| The page rule | A page (any frame of it) that shows a payment method on file (words, a masked number, a wallet button) next to any price refuses every click, submit and Enter but a plain link, and every check and select. A clickable `<div>` (a click handler, a tabindex, a pointer cursor) counts as a button, and a click is judged through the link or button around the element. |
| Order paths | A link or form aimed at an order path (`ORDER_ACTION_RE`) is refused whatever its words or method. A plain link to `/orders` (an order history) is refused too; `browser.read` can still open that address. |
| Languages | Purchase words, "ending in" phrasings and total labels in German, French, Spanish, Portuguese, Italian and Dutch, and in Japanese, Chinese, Korean and Hindi (matched without word boundaries); the masked number, the wallet, the price and the order path do not depend on the language. |
| Look-alike hosts | A well-known brand as any label of the host, or a hyphenated part of one, on another registrable domain is refused (`amazon.com.evil.com`, `www.paypal.com.secure-login.xyz`, `ticketmaster.evil.com`). A real shop that uses a brand word as a subdomain of its own domain is refused as well; the owner is told to open the site themselves. |
| The daily cap | `purchase_approved` counts until its outcome row (same `checkout_id`) settles it; the approval row is written before the vault opens, and a failed write refuses the checkout (`check_failed`) with nothing filled. A failed outcome write is logged at error level and can only over-count. |
| Residuals | Accepted: a page's own XHR, fetch or beacon is not judged (hosted payment scripts need it in the checkout window; outside it, a field whose script orders by `fetch()` is not stopped). A GET navigation to another origin during the bound checkout window is admitted. A frame that posts by itself (3-D Secure) after the checkout window closes and before the handoff opens may be stopped. A shop that shows a wallet button (Shop Pay) next to a price refuses "Add to cart" and every choice through `browser.act`. Not covered yet: a read-tier `browser.read` click on a non-consequential GET link to an order path is followed (§6 "Money paths"). §14 closes the last and narrows the first. |

## 14. Changes after the money-path review of 2026-09-25

The review that followed §13 found orders placed through `browser.read` (no approval card at all), through `browser.act` clicks judged by the element named rather than the one the click reaches, through a submit judged by one button and sent by another, through an Enter on a focus the judge could not classify, through review pages written in shapes and languages the patterns did not read, and look-alike hosts that glue a brand to another word. Each rule below has a test that failed before and passes after (`tests/test_browser_act.py` "routes around the purchase rules", `tests/test_browser_guard.py`, `tests/test_browser_markers.py`, `tests/test_checkout_merchant.py`).

| Area | Rule |
|---|---|
| `browser.read`'s click | After the guard's consequential check, the click is judged by `markers.PURCHASE_TARGET_JS` with every frame's facts joined in, the judge `browser.act` uses. It is refused ("use browser.act", `consequential` saying it may place an order) whenever `browser.act` would refuse it as `use_checkout` (a link only when it is aimed at an order step: an order history is read), and on any button of a page that shows a price next to an order total or a payment method on file. A button on a page that only shows prices (a product page) is still clicked. |
| Order steps | `markers.ORDER_STEP_RE` (/place-order, /submit_order, /confirm-order, /checkout/complete, /checkout/confirm…) is the part of `ORDER_ACTION_RE` whose mere opening may be the order. With no write window and no handoff open, the guard aborts any navigation of any frame to one (a model's `open`, a link, back, a redirect's target) and any non-GET request a page script sends to one (`fetch`, XHR, a beacon). While `browser.act` changes something (`changing`), a page script's non-GET request to any order address is aborted and the act refused as `auto_submit`. A GET, a request to any other address (suggestions, analytics) and anything inside a write window or a handoff pass. |
| Where a click lands | The element under the point Playwright clicks is judged, followed into open shadow roots; a `<label>` as the control it is for (`label.control`); a point outside the element answers the element itself unless it holds a control of its own; a shadow host whose tree cannot be read refuses. |
| One default button | The default button is the form's first submit control among `form.elements` (tree order, a `form=` button before the form included) in the page memory, `SUBMIT_TARGET_JS` and `ENTER_TARGET_JS`, and `browser.act submit` sends the form through that same button (`form.requestSubmit(button)`), so the formaction and words sent are the ones judged. |
| Enter | Any focused element that is not a field is judged as the control, by its own words, button-likeness and link. A focused element that cannot hold a focus itself (the focus is inside a closed shadow root) and a closed-root host refuse. |
| Unreadable pages | A custom element that takes room on screen with no shadow root, children or text of its own is a closed shadow root: every fact of its page counts as shown. A total label whose amount is an image counts as a total. |
| Wider patterns | Masked cards written `...4242` or `…4242`; "default", "primary" and "preferred" card or payment; every Unicode currency sign, the ISO 4217 codes (less ALL, AMD, BAM, BOB, CUP, GEL, MAD, MOP, PEN, SOS and TOP, which are English words) and 円, 元, 원, kr, zł, Kč, lei, руб, грн, ر.س, د.إ; totals in Russian, Arabic, Hebrew, Polish and Turkish; purchase words for rent, donate, pre-order, reserve, request to book, place bid, upgrade and renew, and in Russian, Arabic, Hebrew, Turkish, Polish and Swedish (whole words) and 確定, 提交订单, 确认订单; a button that is little more than a price (at most two other words, never "Add to cart") is a purchase. |
| Look-alike hosts | A label is also compared as it reads (rn as m, vv as w, cl as d, 0/1/5 as o/l/s: arnazon.com), and a brand glued to another word in any label or hyphenated part is refused: at the start or end from four letters (nikestore, paypalsecure, appleid-verify, amazonprime-deals, ticketmasterresale, bestbuyoutlet), anywhere inside from five ("nike" in "moniker", "ulta" in "consultant" and "etsy" in "betsyjohnson" are not). A real shop whose name starts or ends with a brand word (applebees.com, deltafaucet.com, zoominfo.com) is refused as well; the owner opens it themselves. |
| Residuals | Accepted: a page script's request to an address that is not an order step is not judged outside a change (a script button that orders at `/api/cart/checkout` on a page with no price, no total and no payment method in any form the patterns read is followed at read tier). A button on a page that only shows prices (no total, no payment method) is clicked at read tier; one that is little more than a price is not. The closed-root rule reads custom elements only (a closed root on a built-in `<div>` is not detected). Word lists stay word lists: a language or a phrasing not listed is caught only by the page signals (a masked card, a wallet, a total, an order path). |

## 15. The guarantee that can be proven (2026-09-25)

Four review rounds kept finding pages the patterns did not read. The guarantee in §6 "Money paths" is now the one the code can be checked against: no money moves without the owner seeing the page on an approval card first, and card data is only ever entered by `browser.checkout`. Every heuristic stays as defence in depth (the 51 adversarial probes of the reviews still pass). Each row has a test that failed before and passes after (`tests/test_browser_act_card.py`; the registry, gating and wiring tests updated).

| Area | Rule |
|---|---|
| Acting is its own switch | `browser_act` ("Fill in forms and click on sites"): off by default, high risk, native Mac/Windows only, `requires=("browser_control",)` (the report shows it blocked with "Needs 'Control a browser' on in Permissions." while that is not on). It claims `browser.act`, which leaves `browser_control`'s claims; `_REQUIRED_CAPABILITIES[("browser", "act")] = ("browser_control",)`, so the offer, the permission check and the dispatch refuse it on either switch. An install that had "Control a browser" on keeps reading and does not gain `browser.act` on upgrade (a stored row without the key reads as the default, off). |
| Every act card shows the page | `bind_async` takes the picture at card time (target outlined in a 3px red box, secrets masked), kept in memory only; `approval_image` serves it to the web card (`ApprovalPicture`) and to Telegram, where the card is a photo captioned with its sentence and the Approve/Deny keyboard (`/pending` re-sends it the same way). A failed capture still makes the card, with "No picture of the page could be taken." |
| Money warning | From the joined frame facts and the target judge: an order total (its amount when the total line parses), a saved payment method, a wallet button, a frame that could not be read, or a target matching a purchase pattern that did not refuse it, adds "This page shows … This step may place an order. Crawler normally pays only through its checkout step." |
| Reading never orders | `browser.read`'s click only follows a plain GET link that is no order path (an order history aside), or clicks a control outside any form with no purchase words on a page with no order total, payment method on file or wallet (`markers.read_click_allowed`); everything else is refused with "Reading can't click that. Ask to fill in forms and click (needs 'Fill in forms and click on sites' in Permissions)." A script button that orders by `fetch()` on a page whose total is a picture, and one inside a form, are now refused; "Show more flights" on a results page is still clicked. While the click runs, and until the network is quiet after it (250 ms with no request in flight, at most 2 s), no page script sends anything but a GET or a message on the page's own WebSocket, no request goes to an order path and no frame opens one; a click whose script tries is answered the same way. |
| No order request without a card | Outside a write window no page script sends to an order address (`ORDER_ACTION_RE`, a query or fragment after it included): a script button's `fetch('/orders', {method: 'POST'})`, a page that orders on load or when scrolled to. No request of any method opens an order step (`ORDER_STEP_RE`): `new Image().src = '/place-order?sku=1'` and a GET `fetch('/checkout/complete')` are stopped like a navigation there. No WebSocket message goes out on a page's socket whose address is an order address (a worker's socket is residual 1 in §6). The model's `browser.read handoff` opens the page to the person's sign-in, not to an order step or an order address; only the checkout's handoff after the approved order does (3-D Secure). |
| Every window is its page's | The write window (`write_allowed`, `write_origin`) is opened for the card's page (`write_page`) and the checkout's handoff for its page (`handoff_page`); a request from another tab, a worker, or a frame whose page cannot be told is outside it. Approving "Add to cart" on one tab no longer lets a background tab's `fetch('/place-order', {method: 'POST'})` through (tests in `tests/test_browser_act.py` and `tests/test_browser_guard.py`, the WebSocket one over plain `ws://` to the fake site). |
| The window is the approved page's | Inside an approved act's or checkout's window (and the checkout's handoff), a navigation of the approved tab passes only when its Origin, or its Referer when the Origin is missing or "null", is the origin of the page open in it; one with neither passes only while the tab is the session's only one (`guard._started_by`). A tab of another site that opened the shop with `window.open` cannot point it at /place-order when the approved click lands, directly or through a page of its own that would open the step as the tab's own (`OTHER_PAGE_NAVIGATION`; `test_inside_a_window_only_the_approved_page_navigates_its_tab` in `tests/test_browser_guard.py` for both windows, `test_another_sites_tab_cannot_point_the_approved_tab_at_an_order_step` in `tests/test_browser_act.py`, direct and through a page of its own). |
| Every act is bound to the page | The card keeps the page's address (a digest, never the query string) with its origin and outline; every approved act, a key press included, is refused (`outline_changed`) when the page open now is not that page. A card whose picture is no longer kept (its TTL is the approval's, `APPROVAL_TTL_MINUTES`) says so and is refused (`picture_gone`). |
| Residuals | As listed in §6: a page script's requests on the card's page during an approved act are not judged, nor, outside a read-tier click's window, one to an address that is no order path (a delayed script POST after the quiet window; a page's own requests on open, as in the owner's browser); a page's own sub-resource or frame request that redirects to an order step is not followed hop by hop (cross-site it carries no SameSite=Lax cookies, same-site it is the shop acting on itself), and a worker's WebSocket is not routed; the patterns may miss unusual pages, so the picture, not the warning, is what the owner approves on; a read-tier plain link to an address that is no order path is followed; the picture is the viewport at card time. |
