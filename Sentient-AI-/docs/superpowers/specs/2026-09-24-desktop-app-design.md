# Crawler AI desktop app (v1) — design

**Date:** 2026-09-24 · **Status:** proposed · **Owner decision:** Tauri 2, one app for Mac and Windows.

## 1. Goal

A normal app people download and double-click — `Crawler AI.dmg` on Mac, `Crawler AI Setup.exe` on Windows — that installs, starts and opens Crawler AI with no Terminal, no `.env` editing and (once signed) no security warning. It replaces the browser-page bootstrap for end users; the bootstrap and the copy-paste commands stay for developers.

v1 runs Crawler AI in Docker Desktop, as today. v2 (separate project) runs the backend natively and holds OS permissions (Screen Recording, headed browser) — the app is built so v2 slots in.

## 2. What the user sees

1. **Download** the `.dmg` / `.exe` from GitHub Releases, open it, drag to Applications / run the setup.
2. **First launch** — a native window with the same four steps as the bootstrap page:
   1. *Check this computer* — Docker Desktop installed and running (with an "Open Docker Desktop" button and a download link), Compose v2, ports 3000/8000/5432/6379, disk space. Windows: WSL 2 note.
   2. *Security keys* — "Generate for me" (default) or "Use my own" (two masked fields with format rules).
   3. *Install & start* — live log, phase line and elapsed time; ends with "Crawler AI is running".
   4. *Open* — the app window **becomes Crawler AI** (the web app loads inside the window; the setup wizard takes over: owner, AI provider, Telegram, permissions).
3. **After that** — launching the app opens Crawler AI directly. A tray / menu-bar icon offers: Open Crawler AI · Start · Stop · Show logs · Check for updates · Quit. Closing the window keeps the tray icon; Quit stops the app, not the stack (a setting "Stop Crawler AI when I quit" defaults off).

## 3. Architecture

```
desktop/
  src-tauri/            Rust: the app process
    src/main.rs         window + tray setup, single instance, menu
    src/preflight.rs    Docker/Compose/ports/disk checks (a CommandRunner trait so tests fake it)
    src/keys.rs         generate / validate SECRET_KEY + ENCRYPTION_KEY, write backend/.env (0600 / owner-only ACL)
    src/stack.rs        extract bundled source → stack dir; docker compose -p crawler-ai up/start/stop/logs; health polling
    src/platform.rs     paths per OS, open Docker Desktop, owner-only file permissions
    src/commands.rs     #[tauri::command] wrappers; events streamed to the UI ("stack://log", "stack://phase")
    tauri.conf.json, capabilities/  (IPC allowed only for the bundled setup window)
  ui/                   Vite + React + TS: the four-step setup + status screen (no external resources)
  stack/                build-time copy of backend/, frontend/, docker/ (generated by a script; not committed)
```

- **Bundled source.** The Crawler AI source (backend, frontend, docker — no `node_modules`, no `.env`, no tests; a few MB) is packed into the app as a resource at build time. On install the app copies it to the stack directory for that version and runs Compose there. The app's code signature therefore covers the exact code that gets built — nothing unsigned is downloaded except Docker's base images. App version = Crawler AI version.
- **Stack directory:** Mac `~/Library/Application Support/Crawler AI/stack/`, Windows `%LOCALAPPDATA%\Crawler AI\stack\`. `backend/.env` lives there with owner-only permissions; keys are never logged or sent to the UI after saving.
- **Compose project name:** `crawler-ai` (same as the bootstrap), so the app, the bootstrap and CLI all manage the same stack; data volumes persist across app updates.
- **Two windows, two trust levels.** The setup/status window loads the bundled UI and is the only one allowed to call app commands. The Crawler AI window loads `http://localhost:3000` with **no IPC access** (Tauri capabilities are scoped to the setup window's label), so a page in the web app can never start or stop the stack or read files.
- **Single instance:** a second launch focuses the existing window.
- **Updates (v1):** "Check for updates" compares the running version with the latest GitHub Release and opens the download page. The signed in-app updater (Tauri updater with its own signing key) is v1.1, once the update key is created and stored as a GitHub secret by the owner.

## 4. Signing and distribution

- **Mac:** Developer ID Application certificate + notarization (`APPLE_SIGNING_IDENTITY`, and either an App Store Connect API key or `APPLE_ID`/`APPLE_PASSWORD`/`APPLE_TEAM_ID` as environment variables set by the owner — never committed, never handled by agents). Hardened runtime; entitlements only for what v1 needs (outbound network, run child processes). Until the certificate exists, local builds are ad-hoc signed; beta testers click Open Anyway once.
- **Windows:** unsigned `.exe` (NSIS, per-user install, no admin) built by CI; SmartScreen "More info → Run anyway" until an Authenticode certificate (Azure Trusted Signing or OV) is added.
- **Releases:** a GitHub Actions workflow (`desktop.yml`) builds the Mac universal `.dmg` and the Windows `.exe` on `workflow_dispatch` and on tags `desktop-v*`, runs the tests, and uploads to a **draft pre-release** ("beta"). Signing steps run only when the signing secrets exist.

## 5. Security

- The app never sees the AI provider key or the Telegram token — those are entered in the in-app wizard and stored by the backend, as today.
- `SECRET_KEY` / `ENCRYPTION_KEY` are generated with the OS CSPRNG, written once to the stack's `.env` with owner-only permissions, never logged, never returned to the UI.
- Child processes (`docker compose …`) run with an allowlisted environment and argv arrays (no shell).
- CSP on the bundled UI: `default-src 'self'`; no remote scripts. The Crawler AI window is a separate webview with no command access.

## 6. Testing

- Rust unit tests (`cargo test`, Mac and Windows in CI): key generation/validation, `.env` writing and permission bits (ACL call mocked on Windows), preflight parsing (Compose version, `compose ls` JSON, port checks), stack phases with a fake `CommandRunner`, health polling with a fake HTTP probe, path selection per OS.
- UI tests (vitest): each step's states (pass/fail/retry), key form validation, log streaming render.
- Manual on this Mac: `npm run tauri dev`, then a local `tauri build` → install the `.dmg` → full flow with the live stack stopped. Windows: install the CI `.exe` on the team's Windows VM.

## 7. Out of scope for v1

Native (no-Docker) backend, OS permission prompts, headed browser, auto-updater, Windows code signing, Linux build.
